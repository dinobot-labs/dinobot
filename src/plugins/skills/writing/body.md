# Writing — 기술 글쓰기와 윤문

기술 블로그 글, 공개 아티클, 뉴스레터 원고, 긴 기술 문서를 새로 쓰거나 이미 쓴 글을 다듬을 때 이 스킬을 따른다. 목표는 하나다: **전문 지식이 없는 독자도 중간에 포기하지 않고 끝까지 읽을 수 있는 글.** 말투의 원형은 roach-newsletter `archive/WRITING.md`다.

## 1. 독자와의 약속

1. 첫 문단에서 독자가 무엇을 얻어 가는지 말한다. 자랑이나 서론 미끄러뜨리기는 하지 않는다.
2. 어려운 용어가 처음 나오면 그 자리에서 한 문장으로 푼다. 문서 뒤쪽에서 설명하지 않는다.
3. 한 문단에는 하나의 생각만 담는다. 문장이 세 줄을 넘으면 나눌 수 없는지 본다.
4. "아는 사람만"이라는 글을 만들지 않는다. 수식·기호·영문 약어는 읽는 법과 뜻을 곁들인다.

## 2. 말투 (Roach voice)

- 기본은 존댓말(`~습니다`, `~합니다`)이되 구어체를 섞는다: `~죠`, `~거든요`, `~해요`, `~일까요?`.
- 문장 시작 접속어로 리듬을 만든다: `근데`, `그래서`, `즉,`, `하지만`, `그렇다면`.
- 독자에게 직접 말을 건다: `여러분`, 수사적 질문(`왜 그럴까요?`, `이거 어디서 많이 보셨죠?`), 함께하기(`정리해 봅시다`, `한번 ~해 봅시다`).
- 어려운 개념 앞에서 부담을 낮춘다: `어렵지 않게 설명해 보겠습니다`, `조금만 참아 봅시다 :)`.
- 이모티콘 `:)` 은 가끔. 문단마다 쓰면 과하다.
- 영어 용어는 괄호 병기: 하네스(Harness), 검증관(verifier), 궤적(trajectory). 이미 굳은 외래어(API, 토큰, 컨텍스트)는 그대로 쓴다.
- 사실과 의견을 분리한다. 추측은 반드시 표기한다: `제 추측으로는`, `~일 것 같아요`.

## 3. 구조

제목(짧고 실용적) → 부제(글의 관점 한 줄) → 도입(개인적 관찰이나 최근 사건으로 시작, `오늘은 ~에 대해 이야기해 보려고 합니다` 식 예고) → 본문(h2 섹션들, 섹션마다 개념 → 예시 → 실전 적용 순서) → 마치며(요약 + 다음 편 예고 + `항상 읽어주셔서 감사합니다 :)`).

- 수치·출처·논문은 본문 `[N]` 각주로 처리하고 하단에 모은다.
- 어려운 표현에는 풀이 각주를 단다. 이때 본문의 문체는 유지하고, 각주는 말하듯 푼다(`~예요`). 웹이라면 각주 번호에 마우스를 올리면 내용이 보이게(title 속성) 하면 더 좋다.
- 영어 인용문은 원문 그대로 쓰고 바로 뒤에 풀이를 단다.

## 4. 그림과 도식

- 개념 설명이 필요한 지점마다 그림 후보를 찾는다. 장문 아티클이면 그림 10개 이상도 아깝지 않다. 글자로 세 문단을 써야 할 내용이 도식 한 장으로 끝나는지 늘 묻는다.
- 픽셀아트 AI 이미지 같은 장식 대신 **이해를 돕는 설명 도식**을 직접 만든다. 정적 HTML이면 인라인 SVG가 기본이다.
- 색은 CSS 변수(`--panel`, `--ok`, `--bad`, `--warn`, `--accent` …)로 써서 다크 모드에서 자동 대응하게 한다. 상태 색은 글 전체에서 일관되게: 성공=초록, 실패/위반=빨강, 경고=노랑, 사용자/사람=보라, 강조/에이전트=파랑.
- 그림마다 `그림 N.` 번호 캡션을 달고, 캡션이 그림만 봐도 이해되게 쓴다.
- 도식이 넓으면 모바일에서 가로 스크롤(+안내 문구)을 제공한다.

세부 규칙은 `references/figures-and-media.md`에서 읽는다.

## 5. 강조

- 핵심 용어는 `<b>`, 핵심 문장은 하이라이트. 하이라이트 색 약속: 노랑=핵심 주장/결론, 파랑=추측·개념어, 초록=기법 이름, 빨강=주의.
- 같은 문장에 강조를 겹치지 않는다. 하이라이트가 스무 문장마다 나오면 강조가 아니다.

## 6. 사실과 민감정보

- 모든 수치는 원천 데이터·코드와 대조한다. 불일치가 0일 때만 전달한다.
- 공개 글에는 대화 ID·세션 식별자, 로컬 경로, 실명, 토큰을 넣지 않는다. 집계값만 담고, 예시 속 사례는 일반화한다. 전달 전에 grep으로 스캔한다(`references/verification.md`).
- 근거 없는 수치·과장 표현(`혁명적인`, `게임 체인저`)은 쓰지 않는다.

## 7. 전달 전 검증

기본 산출물은 **완성된 로컬 HTML(또는 원고)** 까지다. 블로그 게시·배포(push, Pages) 같은 공개 작업은 사용자가 요청했을 때만 한다. 게시하든 전달하든 검증이 끝난 뒤에 한다.

1. HTML이면 태그 균형, 중복 ID, 깨진 앵커 검사에서 오류 0건.
2. 데스크톱(1280px)·모바일(375px, headless 창 폭이 아니라 iframe 래퍼로 실측)·다크 모드 스크린샷에서 가로 넘침 0.
3. 로컬 산출물이면 CSS·아이콘 같은 상대 경로 자원이 모두 해석되고, 게시했다면 링크·CSS·RSS 등 자원이 모두 200.
4. 문체 점검: 존댓말 혼용, 각주 번호 본문↔하단 일치, 마무리 인사.

명령어 예시는 `references/verification.md`에서 읽는다.
